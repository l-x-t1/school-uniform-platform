## 1.xfpt_after_sale（售后主表）

用来记录一笔售后申请的全过程

**字段含义：**

id

这条售后记录自己的编号，**主键**，系统内部唯一识别一条数据。

after_sale_no
售后单号，给业务看的一串编号，一般用来**查售后单**。

order_id
关联的订单主表 ID，说明这笔售后属于哪个**订单**。

order_item_id
关联的订单明细 ID，说明售后针对订单里的哪一个**商品**明细。

order_no
**订单编号，方便直接展示和查询**，不一定非得每次都去订单表再查。

order_type
**订单类型**，表示这笔订单属于哪种业务类型。

school_id
**学校** ID，说明这笔业务归属哪个学校。

supplier_id
**供应商** ID，说明这笔售后涉及哪个供应商。

user_id
**用户** ID，发起售后的用户是谁。

user_name
**用户名**，冗余存一份名字，方便直接展示。

student_name
**学生姓名**，如果这个业务和学生尺码、校服有关，这个字段就是对应学生名字。

apply_type
申请类型，就是**售后类型**。
比如可能表示：
退款
换货
退货退款
仅退款
具体要看系统怎么约定。

target_size_id
目标尺码 ID，说明售后可能和**尺码调整**有关。

target_size_name
目标**尺码名称**，比如 160、170、L 这种，方便展示。

reason
**申请原因**，用户为什么要申请售后。

images_json
**图片凭证**，一般存图片地址列表或 JSON 数据，比如破损照片、尺码不符截图。

apply_num
**申请数量**，申请售后的件数是多少。

apply_amount
**申请金额**，这次售后申请想退多少钱。

status
**售后状态**，表示这笔售后现在进行到哪一步了。
比如可能是：
待审核
已通过
已驳回
已完成
已关闭
具体值要看系统定义。

====

audit_by
**审核人**，谁审核了这笔售后。

audit_time
**审核时间**，什么时候审核的。

handle_result
**处理结果**，比如同意退款、驳回申请、换货处理之类。

handle_remark
**处理备注**，对这次处理的补充说明。

finish_time
**完成时间**，这笔售后什么时候真正结束。



dept_id
部门 ID，一般是系统组织架构里的部门标识。

ancestors
祖级列表，通常是部门层级路径，比如上级部门链路，常见于权限系统。











**下面是通用审计字段**

create_by
创建人，这条数据是谁创建的。

create_time
创建时间，这条售后记录什么时候生成。

update_by
更新人，最后一次是谁改的。

update_time
更新时间，最后一次修改时间。

remark
备注，补充说明。

del_flag
删除标记，一般不是物理删除，而是逻辑删除。

考虑售后状态是否要添加详细的内容，比如补充退款结果字段，如实际退款金额、退款时间、退款状态  ==（加上）==



## 2.xfpt_comment（评价表）

用户对订单或商品的评价信息

**字段含义：**

id
**主键**，自增。

order_id
关联**订单主表**。

order_item_id
关联订单明细，说明评价可以精确到某个**商品**明细。

order_no
**订单编号**，方便展示和查询。

goods_id
**商品 ID**。

goods_name
**商品名称**，冗余展示字段。

user_id
**评价用户 ID**。

user_name
评价**用户名**，冗余展示字段。

supplier_id
**供应商 ID**，说明评价还能关联到商家维度。

score
**评分**，tinyint unsigned 很适合做 1-5 分这类评分。

content
**评价内容**，文字评价。

images_json
**评价图片**，longtext 存 JSON/路径，设计方向是对的。

reply_content
**商家回复**内容。

reply_time
商家**回复时间**。

status
**评价状态**，比如待显示、已显示、已隐藏、已删除之类，具体要看业务定义。

create_by、create_time、update_by、update_time、remark、del_flag
这些还是通用审计字段



从业务结构上看，该表已包含评价内容、评分、图片、商家回复、状态以及创建更新时间等通用审计信息，整体能够支撑订单完成后的评价与回复场景，且图片字段方案符合统一校验要点中“避免直接使用 blob/base64 长期存储”的要求。



## 3.xfpt_finance_flow（资金流水表）

这张表负责**记录资金流动**，哪种业务产生了这笔钱，关联哪个订单/售后、涉及哪个用户或供应商、金额是多少、支付渠道是什么、交易单号是什么、状态如何、发生时间是什么时候。

**字段含义：**

- id：**主键**，自增
- flow_no：**流水单号**，唯一编号（这是系统对应的单号）
- business_type：**业务类型**，比如支付、退款、提现、结算等
- order_id：**关联订单**
- after_sale_id：关联**售后单**
- school_id：**学校** ID
- supplier_id：**供应商** ID
- user_id：**用户** ID
- amount：本次流水**金额**
- pay_channel：**支付渠道**，比如微信、支付宝之类
- trade_no：外部交易单号或平台交易号（这是外部平台对应的单号，比如微信、支付宝那边对应的单号）
- status：流水状态（表示这笔订单处于待支付、支付成功等状态）
- trade_time：交易发生时间
- dept_id、ancestors、create_by、create_time、update_by、update_time、remark、del_flag：通用管理字段



**改进意见：**

* 这张表只记录了流水金额，可以增加具体的，是收入还是支出。==（加）== （运费？）

## 5.xfpt_school_message（学校信息表）

这张表记录学校的基础信息，包括学校名称、地区、地址、学校类型、校徽、负责人、在校人数等。学校信息完善入口会写入这张表。

这次重新设计后，银行卡账户直接作为学校基础资料挂到 `xfpt_school_message`。

新增字段：

- bank_account_name：银行账户户名
- bank_name：开户银行
- bank_branch_name：开户支行
- bank_account_no：银行卡号

设计意见：

* 学校银行卡账户不要放在 `sys_dept`。`sys_dept` 是组织架构表，主要负责部门树、学校标识、状态等通用组织信息。
* 学校银行卡账户也不建议用 JSON 存。银行卡号、开户名、开户行后续可能需要表单校验、模糊查询、导出、脱敏展示，独立字段更合适。
* 银行卡号属于敏感信息，前端列表和详情页后续建议做脱敏展示，例如只显示后四位。
